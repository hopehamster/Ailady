## 2. Tier-1 actions — code-grounded analysis

### T1.A — Extend `promptInjectionGuard` to scan retrieved memory + lorebook

- **Restatement:** Indirect injection via persisted memory/lorebook content; today's guard only scans user input.
- **Gap in code:**
  - `promptInjectionGuard.ts:90 scanUserInput()` is the only public scan function. No `scanRetrievedContext()`.
  - Memory retrieval: `services/memoryService.ts:2581 recallSemanticMemories()` returns `SemanticMemoryRecall[]` whose `text` field flows directly into prompt assembly. No sanitization.
  - Lorebook retrieval: `services/lorebookService.ts:65 getActivatedLoreSnippets()` returns `ActivatedLoreSnippet[]` with raw `content`. No sanitization.
  - Concatenation site: `services/promptAugmentService.ts` imports both (`recallSemanticMemories` L10, lorebook from L21) and assembles them into the prompt context.
- **Current state:** Nothing exists. Persistent attack vector confirmed.
- **Change-set:** add `scanRetrievedContext(text, source)` to `promptInjectionGuard.ts` (~30 LOC, reuse `OUTPUT_PATTERNS` plus expanded memory-poisoning patterns). Call it from `promptAugmentService.ts` for every retrieved snippet BEFORE concatenation. Strip or redact `high`-severity findings, tag medium for audit.
- **Effort:** ~2h confirmed.
- **Risk if shipped:** **low** — read-only filter on already-stored data; no schema change.

### T1.B — Cross-tenant memory isolation regression test

- **Restatement:** Verify per-user memory filtering ALWAYS fires; no codepath retrieves before filtering.
- **Gap in code:**
  - `memoryService.ts:2562` and `:2611` both `.where('userId', '==', userId)` BEFORE `.get()`. This is "filter at query time on a shared collection," not Firestore native vector search.
  - `userId` flows from `context.auth.uid` UNLESS the **dangerous fallback at `index.ts:222-227`** kicks in: `if (!userId && data.userId) { userId = data.userId; }` — a client can pass any `data.userId` and become that user when auth context is null. This is a STRIDE-Spoofing bug not flagged in the STRIDE doc.
- **Current state:** Partial. Filter exists everywhere I could find; the client-controlled-uid bypass is the real risk surface.
- **Change-set:** (a) new `test/security/crossTenantMemory.test.js` exercising User A query while User B fresh; (b) **separately, fix `index.ts:222-227`** — log + reject when `context.auth?.uid` is null instead of trusting client `data.userId`. Document the test against the bypass.
- **Effort:** ~2h for test, ~30min for the auth fallback fix. Total under T1.B envelope.
- **Risk if shipped:** **medium** — the auth-fallback fix could break any code currently relying on the bypass (e.g. integration tests). Grep before deleting.

### T1.C — Output-handling sanitization layer

- **Restatement:** LLM output flows to TTS, memory writeback, Flutter rendering with no sanitization layer.
- **Gap in code:**
  - `promptInjectionGuard.ts:119 scanModelOutput()` exists but is **not imported anywhere** outside its own test file. Output scan is implemented and dead-coded.
  - `services/voiceService.ts` (1632 LOC) — no SSML strip layer; TTS receives raw model output.
  - `services/postResponseOrchestrationService.ts` (234 LOC) — writes back to memory; no "ignore previous" filter.
  - `services/responseFinalizationService.ts` (136 LOC) — last touchpoint before client; no markdown allow-list.
- **Current state:** Partial — scanner exists, no callers. Lower effort than synthesis assumed.
- **Change-set:** wire `scanModelOutput` into the three services. Add SSML allow-list to voiceService (likely 15–25 LOC). Add memory-writeback refusal pattern to postResponseOrchestration (10 LOC). Markdown allow-list in responseFinalization (~30 LOC).
- **Effort:** ~3h (less than synthesis's 4h since the scanner is already built).
- **Risk if shipped:** **medium** — SSML strip could affect any voice expressiveness features depending on the allow-list breadth.

### T1.D — Per-turn reconstructability trace

- **Restatement:** A `turnId` threaded through all 9 services + Firestore subcollection capturing inputs/context/tool-calls/output.
- **Gap in code:** Grep for `turnId|traceId|requestId` across `functions/src` returns **zero matches**. Nothing exists.
- **Current state:** Nothing exists.
- **Change-set:** new `services/turnTraceService.ts` (~120 LOC). Generate `turnId` at top of `generateResponse` callable (`index.ts:210` body). Firestore TTL via `gcloud firestore fields ttl` on `ts` field.

- **Risk if shipped:** **low** — additive only; trace writes are fire-and-forget.

### T1.E — HITL preapproved-phrase pool for crisis topics

- **Restatement:** Route self-harm / medical / legal / financial topics to curated phrase pools, bypass free generation.
- **Gap in code:**
  - `conversationPolicyService.ts:48 detectConsentSensitiveTopic()` regex covers `trauma|abuse|self-harm|suicide|panic attack|assault|grief|deeply personal`. The function returns a boolean and adjusts pacing — it does **NOT route to a phrase pool**. Free generation continues; the model just gets a "consent-sensitive" tag.
  - `services/llmService.ts:2934 shouldReturnOutOfScope()` bypasses generation for `debug|code|tax|legal|...` but **NOT for self-harm / medical**. Note: out-of-scope returns at L2934–2942 is a one-line `buildOutOfScopeResponse()` not a curated phrase pool.
  - **No `crisis*.ts`, no `safety_resource*`, no `988`/`hotline`/preapproved phrase pool anywhere in `functions/src/` or `tools/girlai2/lib/`.**
- **Current state:** Detection regex exists in conversationPolicyService; NO routing, NO phrase pool, NO crisis-resource card.
- **Change-set:** new `safety/crisisRouter.ts` + `safety/crisisPhrases.json`. Hook in `llmService.generateAIResponse` BEFORE `shouldReturnOutOfScope` — if crisis match, return curated phrase + Flutter-side `crisis_resource_card` payload field. Flutter UI handles the card.
- **Effort:** ~4h confirmed (phrase content is the unknown — see Q1).
- **Risk if shipped:** **high** if phrases are wrong (could read as cold/dismissive to a tester in distress). **low** technically.

### T1.F — App Check enforcement on every callable

### T1.G — Hard timeout + per-turn tool-call ceiling on LLM calls

- **Restatement:** 30s `AbortController` per provider call + `enforceToolCallBudget(conversationId, max=5)`.
- **Gap in code:**
  - `services/llmService.ts:2527` has stage-timeout via `setTimeout` + `reject` pattern (`stageName_timeout_after_${budgetMs}ms`). This is a Promise.race, NOT an `AbortController` — the underlying HTTP request keeps running and burning tokens even after the race resolves. Cost-bomb gap remains real.
  - L3467 / L3534: `timeoutMs: latencyBudgets.responseMs` is passed to provider helpers but no grep result for `AbortController` or `AbortSignal` anywhere in the service.
  - No `enforceToolCallBudget` exists. `rateLimit.ts` only counts requests/tokens/voice-chars per UTC day, not per-conversation tool-call count.
- **Current state:** Soft timeouts (Promise.race) without actual call cancellation; no tool-call ceiling.
- **Change-set:** swap each provider helper's internal `fetch`/SDK call to use `AbortController.signal`; abort on race timeout. Add `enforceToolCallBudget` to `rateLimit.ts` (~25 LOC). Per-conversation Firestore counter.
- **Effort:** ~3h (synthesis 2h was optimistic — provider helpers are spread across the 3721-LOC llmService).
- **Risk if shipped:** **low** — Promise.race already exists; replacing the body of those with AbortController is mechanical.

## 3. Open questions — sourced answers

### Q1 — Crisis HITL: what's there today?
**Answer:** `conversationPolicyService.ts:47 detectConsentSensitiveTopic()` is the only existing surface. It's a regex matcher (`trauma|abuse|self-harm|suicide|panic attack|assault|grief|deeply personal`) that returns a boolean used to adjust pacing/depth in the policy layer. **It does NOT bypass generation, route to phrase pool, or surface crisis resources.** No 988, no hotline strings, no `safety_resource*` collection anywhere in `functions/src` OR `tools/girlai2/lib`. T1.E is greenfield. Founder recommendation per synthesis: ship option (c) — minimal "I'm here, but for this please contact [resource]" + crisis-resource card — for closed beta.

### Q2 — Vector storage architecture
**Answer:**
**(a)** Shared-collection-with-filter, NOT Firestore native vector search. Collection `memoryEmbeddings` (memoryService.ts:385) holds ALL users' embedding chunks. Retrieval does a query+post-filter cosine similarity in Node (memoryService.ts:2620–2640) — NOT Firestore's native vector ANN.

**(b)** userId scoping confirmed at TWO sites:
- Write: `memoryService.ts:2537–2538` `.collection(SEMANTIC_MEMORY_COLLECTION).add({ userId, ... })`
- Read: `memoryService.ts:2611` `.where('userId', '==', userId)` — applied BEFORE `.get()` ✓
- Retention cleanup: `memoryService.ts:2562` same pattern ✓

**(c)** Is there any codepath that retrieves before filtering?
- Within `recallSemanticMemories`: **NO** — the `where` is in the same query as the `.get()` (memoryService.ts:2608–2614). Filter is part of the query, not post-hoc.
- **BUT — STRIDE-Spoofing risk at `index.ts:222–227`:** if `context.auth?.uid` is null and the client sends `data.userId`, the server adopts client-controlled uid for the rest of the request. A malicious client can pass any uid and read THAT user's memory through the legitimate filtered query. This bypasses the filter's security guarantee. **The Firestore filter is correct; the uid plumbing is not.** Recommend fixing as part of T1.B.

### Q3 — Trace retention
Founder decision. Synthesis recommends 90d TTL on `users/{uid}/turnTraces/{turnId}` with indefinite retention for safety-event-tagged turns. Concur. Mechanism: Firestore TTL policy on `ts` field via `gcloud firestore fields ttl set users.turnTraces ts --enable-ttl`.

### Q4 — App Check enforcement
**Answer:** **Configured but unenforced.** Client has full Play Integrity / DeviceCheck setup (`lib/main.dart:73–88`, `pubspec.yaml:19`); server does not enforce on any of 28 callables (grep confirmed). Tokens issued and discarded server-side. Synthesis's Q4 framing was accurate. Recommendation: `unenforced` monitoring mode for 1 week → `enforced` flip after clean signal.

### Q5 — Memory typing: how many buckets today?
**Answer:** `memoryService.ts` `IntelligentMemory` interface (L255–275) declares **18 fields/buckets**, not the synthesis's "one bucket":
1. `coreFacts: CoreFact[]` (personal/relationship/preference/life_event/important_person)
2. `emotionalMoments: EmotionalMoment[]`
3. `conversationSummaries: ConversationSummary[]`
4. `recentContext: {role,content}[]`
5. `scoredMessages: ScoredMessage[]` (importance-weighted, up to 3000)
6. `openLoops: OpenLoop[]`
7. `pacingProfile: RelationalPacingProfile`
8. `sessionArc: SessionArcState`
9. `proactiveConfig: ProactiveMessagingConfig`
10. `styleProfile: UserStyleProfile`
11. `personaConsistency: PersonaConsistencyState`
12. `qualitySnapshots: ResponseQualitySnapshot[]`
13. `weeklyTuningReports: WeeklyRelationshipTuningReport[]`
14. `shadowBenchmarkStats`
15. `behaviorCounters`
16. `openLoopHealth`
17. `chronology: ChronologyState` (events with temporal cues)
18. Separate collection: `memoryEmbeddings` (semantic vector store)

Plus a sophisticated **memoryControllerService.ts:1258 LOC** evidence-precedence framework (`MemoryEvidence`, `MemorySourceKind` with 10 source types, `MemoryActionPlan`, ranked conflict resolution with freshness half-life, canonical-profile-name bonus, etc.).

**Synthesis claim "Aria's `memoryService` treats memory as one bucket" (L743) is wrong.** Aria already has richer typing than the building_ai_remembers 4-bucket model suggests. The real T2.1 work is NOT adding typing — it's deciding whether to align Aria's 18 ad-hoc buckets to the 4 canonical Anderson-style buckets (working/episodic/semantic/procedural) for theoretical cleanness, OR keep Aria's domain-specific decomposition. **Recommend keeping Aria's; downgrade T2.1 to "documentation pass + governor-prompt validation gate on writes" (the part that's actually missing).**

## 4. NEW gaps surfaced during audit

1. **`injectionScan.cleanText` is discarded** (`llmService.ts:2947–2953`). The `<user_message>` delimiter wrapping the synthesis credits as shipped never reaches the model. **Fix: 5min** — swap `userMessage` for `injectionScan.cleanText` in downstream prompt assembly.
2. **Client-controlled-uid fallback bypass** (`index.ts:222–227`). When `context.auth?.uid` is null, server adopts `data.userId`. Defeats every Firestore security rule and the cross-tenant filter. STRIDE-Spoofing critical, missing from the STRIDE doc.
3. **Rate limit covers 1 of 28 callables.** `generateResponse` only. Voice (1632 LOC `voiceService.ts`), vision, memory writes have no per-uid cap. Synthesis says T1.G adds tool-call budget; the underlying gap is wider than that.
4. **`scanModelOutput` is dead code.** Exported, tested, not imported by any caller. Output scan ships "in name only" — 1-line fix to wire into `responseFinalizationService`.
5. **7 audit-log action types declared-but-unused.** `auditLog.ts:8–14` declares `subscription.activated`, `subscription.renewed`, `subscription.cancelled`, `subscription.expired`, `subscription.refunded`, `memory.user_delete`, `onboarding.age_attested`. None are emitted anywhere — RevenueCat webhook handles its events without writing audit entries for state changes. Repudiation surface narrower than STRIDE doc T1.5 claimed.
6. **`responseFinalizationService` has no markdown allow-list.** 136 LOC, no sanitization. Flutter is currently the trust boundary for any malicious markdown the model emits.
7. **Stage timeout uses Promise.race not AbortController.** `llmService.ts:2527`. Tokens keep streaming after the race resolves — DoW (denial-of-wallet) gap not fully closed by per-uid rate limit alone. Synthesis flagged this but worth elevating: this is a *current* spend leak, not a hypothetical.

## 5. Out-of-scope but worth flagging (where Aria is stronger than the notes assume)

- **memoryControllerService.ts (1258 LOC) evidence-precedence framework** — implements ranked conflict resolution with 10 source-kind weights, freshness decay (72h half-life), canonical-profile-name bonus, resolved/expired/suppressed penalties. This is **already** the governor-prompt validation gate the synthesis says is "missing" in T2.2. It needs to be invoked at memory WRITE time (not just read time) and possibly extended with an injection-scan gate, but the precedence engine is built.
- **truthKernelService.ts (1035 LOC)** — exists, audit didn't read it (reference-only per instructions), but its presence means Aria has a dedicated truth-claim adjudication surface most companion apps don't.
- **goldenEvalService.ts (830 LOC)** — golden eval is already a service. The STRIDE doc T1.6 says "Add 5-prompt regression test to goldenEvalService.ts" — it's the natural home and exists.
- **Chronology + open-loops + temporal cues + relational pacing + style profile** are all distinct typed memory layers. The "memory typing refactor" (T2.1) is largely already done; the missing piece is governor-prompt validation on WRITES, not the bucket structure.
